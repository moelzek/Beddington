## Executive summary

The **core is well-built**: the cry state machine, `SootheController`, detector, config validation, and the soothe/assistant logic are clean and genuinely well-tested (318 tests, ~3.7s). But across all eight lenses the verdict is consistent — **Beddington is a strong demo / personal build, not yet a deployable product**, and as shipped it fails its one job in the field:

> **🔴 A Pi that boots delivers zero cry alerts.** The two shipped systemd units run the *camera server* and the *voice assistant*; neither runs the audio→YAMNet→`CryEventTracker`→notifier pipeline, which exists only inside the single-shot `listen`/`analyze` CLI command. There is no continuous monitor service. With auto-soothe on, a detected cry gets *soothed but never alerted*.

Layered on top of that headline: only **one alert per crying episode**, a **desktop-only notifier that silently no-ops on a headless Pi** (degrades to a `print()` into a logfile), **sensors that fail silent** (a dead BME688 looks like a calm nursery), and the flagship `pi-product.toml` points the LLM at a **model `setup_models.sh` never pulls** (so narrator + persona + all voice translation silently break). The README also promises *“no cloud, no streaming, no account”* and that vitals are *“never a product signal”*, while the code ships a LAN MJPEG **video server with Breathing/Heart dashboard tabs**.

None of this contradicts the earlier bug hunt — it's the layer *above* it: deployment reality, product/spec drift, and safety-path wiring that a per-module review can't see.

## Verified NEW findings (19, adversarially confirmed)

### 1. 🔴 CRITICAL — No deployed service runs the cry-alert path — the core monitor is undeployed
*ship-safety · verdict: confirmed*  
**Where:** `deploy/beddington-assistant.service:30, deploy/beddington-liveview.service:40, src/beddington/cli.py:403 (run_pipeline only inside listen/analyze)`  
**What:** The alarm path (audio -> YAMNet -> CryEventTracker -> notifier.notify) lives ONLY in run_pipeline, which is invoked ONLY by the `listen`/`analyze` subcommand at cli.py:403. The two shipped systemd units run `live-view` and `listen-assistant` — neither calls run_pipeline or notifier.notify. `listen` is single-shot (default --seconds 60, cli.py:99) with no wrapper loop and no service. So on a real Pi after boot/reboot, NO process is delivering cry alerts to a parent. The README (line 23/71) markets exactly this: 'listens for sustained crying... before it pings you.' The primary safety promise ships un-deployed. A baby cries at 3am and no notification is ever generated because the alerting process simply isn't running.  
**Fix:** Ship a `beddington-monitor.service` that runs the cry-detect+notify loop continuously (a real long-running loop, not `listen --seconds 60`), with Restart=always and a watchdog. Document mic-arbitration with listen-assistant (only one owner of the mic). Until then, the device is not a working baby monitor.

### 2. 🟠 HIGH — pi-product.toml LLM model (llama3.2:3b) is never pulled by setup — narrator, persona, and all voice intent/soothe translation silently break on the real device
*newbugs-integration · verdict: confirmed*  
**Where:** `config/pi-product.toml:207 (narrator.model) vs scripts/setup_models.sh:13 + src/beddington/cli.py:1169-1173 (_assistant_llm_translator_config)`  
**What:** The 'real final product' profile sets narrator.model = "llama3.2:3b", but setup_models.sh pulls llama3.2:1b (BEDDINGTON_LLM_MODEL default) and default.toml/tier1-demo.toml both use llama3.2:1b. cli._assistant_llm_translator_config() derives the intent/soothe translator from config.narrator, so the SAME 3b model backs (1) morning narrator recap, (2) persona wording, (3) fuzzy question translation, and (4) voice soothe-command translation (translate_soothe_command). On a Pi that ran setup_models.sh and boots with pi-product.toml, every /api/generate call requests llama3.2:3b, which ollama does not have; _ask_ollama_with_options catches the error and returns None, so all four features degrade to fallbacks with no log/alert. This is exactly the profile the docs tell the owner to run for the Lab Witness demo.  
**Fix:** Set narrator.model = "llama3.2:1b" in pi-product.toml (or make setup_models.sh also pull 3b and document the extra ~2GB). Add a startup check that pings ollama /api/tags for the configured model and warns loudly if absent, instead of silently falling back.

### 3. 🟠 HIGH — Dashboard 'playing' state never reconciles with the player subprocess, so a dead/finished soothe player leaves the voice assistant permanently deaf via its self-audio gate
*newbugs-integration · verdict: plausible*  
**Where:** `src/beddington/cli.py:1708-1710 (_DashboardSoothe.playing) + cli.py:903-907/931-934 (soothe_playing poll + _speech_bar)`  
**What:** _DashboardSoothe.playing() returns self._playing, which is only cleared by an explicit stop(). It never checks whether the underlying SubprocessSoothePlayer process is still alive. The voice loop polls /soothe.json every 2s (_dashboard_soothe_playing) and trusts state['playing'] to set soothe_playing=True. When soothe_playing is True, _update_self_audio_floor/_speech_bar RAISE the speech threshold above the (assumed) leaked music. If the loop-player subprocess dies for any reason — mp3 decode failure mid-stream, OOM kill, the 6-hour play_seconds cap at cli.py:1722 elapsing, or SIGKILL — _playing stays set forever. Result: soothe.json reports playing=<name> indefinitely, the assistant keeps its speech bar elevated for silence that no longer contains music, and wake-word/command detection is suppressed until someone manually taps Stop or restarts the service.  
**Fix:** In _DashboardSoothe.playing(), reconcile against player liveness (e.g. expose SubprocessSoothePlayer.is_playing() that checks process.poll()/pid-file) and clear self._playing when no process is alive. Cap the loop far below 6h or add a keepalive the dashboard resets.

### 4. 🟠 HIGH — Background sensor sampler blocks ~2.25s of time.sleep on every tick, saturating its thread and skewing cadence
*perf-pi · verdict: confirmed*  
**Where:** `src/beddington/cli.py:1510 (_SensorSampler._run) -> _read_sensor_snapshot at cli.py:688-709`  
**What:** _SensorSampler._run() calls _read_sensor_snapshot(self._readers) with the DEFAULT warm_seconds=2.0. That function does time.sleep(2.0) then 5x time.sleep(0.05) = ~2.25s of pure blocking sleep per snapshot, plus the actual radar/BME reads. The sampler default interval is 3s (cli.py:297) but real cadence becomes ~5.25s. The history deque maxlen is sized as history_seconds/interval (cli.py:1489) assuming the configured interval, so the '30 min' window silently holds far less history than intended, and the thread spends most of the night sleeping-in-syscall rather than parking on self._stop.wait(). Over a full night this thread is effectively pinned busy-idle instead of sleeping, and the SQLite append cadence (and its fsyncs) is coupled to this inflated period.  
**Fix:** Pass warm_seconds=0.0 in the sampler path (the readers are already warmed once at startup), matching the assistant loop which correctly uses warm_seconds=0.0 at cli.py:1061. Then the snapshot is just the 5x0.05s multi-pass (~0.25s) and self._stop.wait(interval) actually governs cadence.

### 5. 🟠 HIGH — 4GB memory budget likely exceeded when assistant + liveview services run concurrently as shipped
*perf-pi · verdict: plausible*  
**Where:** `config/pi-product.toml:207 (llama3.2:3b) + src/beddington/cli.py:778 (Whisper) + deploy/*.service (two always-on units)`  
**What:** The two systemd units (beddington-assistant + beddington-liveview) are designed to run together. The assistant warms and calls Ollama llama3.2:3b (pi-product.toml:207) which is ~2-2.5GB resident, loads Whisper tiny.en int8 (~75MB but with runtime buffers), builds YAMNet TFLite (auto-soothe), warms Piper TTS (voice_enabled), AND holds a SensorStore SQLite connection. Concurrently the liveview unit runs rpicam-vid MJPEG capture + its own SensorStore + Python HTTP server. On a 4GB Pi 5 with the OS, PipeWire, and page cache, llama3.2:3b resident plus the two Python interpreters plus camera buffers realistically pushes into swap or OOM-kill territory during a multi-hour night — exactly when reliability matters most. default.toml uses the lighter llama3.2:1b, but the product profile ships 3b.  
**Fix:** Either keep llama3.2:1b for the product profile, or gate Ollama so the model is unloaded between narrations (Ollama keep_alive=0) rather than pinned resident; document the measured RSS of both services together and add a swap/zram + memory-pressure check to setup. Consider running Whisper and Ollama in the same process/service so only one heavyweight service is always-on.

### 6. 🟠 HIGH — Always-on phone dashboard re-surfaces radar breathing/heart vitals the README swears are "never a product signal", with no bench_vitals gate on the product surface
*product-roadmap · verdict: confirmed*  
**Where:** `src/beddington/liveview.py:96-97 (DASHBOARD_SENSORS Breathing/Heart); src/beddington/cli.py:1605-1614 (_dashboard_fields vitals) and 2534-2538 (readings_provider)`  
**What:** default.toml:199-204 and the README state the radar's respiratory/heart values are "bench-only... never fed into the spoken recap, never surfaced, never a product signal... product/clinical use needs the Tier-3 gate + sign-off." Yet the live-view dashboard's DASHBOARD_SENSORS declares "Breathing" and "Heart" tabs/graphs, and _dashboard_fields emits a "from radar: breathing ~N, heart ~N" string into the always-on phone readings. The only thing stopping this today is that the radar reader drops vitals unless sensors.radar.bench_vitals=true (sensors.py:264-272). So the moment a researcher flips bench_vitals on for a bench run while the liveview service is up, live vital-sign numbers stream to any phone holding the token — on a surface positioned as a non-medical product, next to a live baby video, which is precisely the "vitals paired as a product/reassurance signal" the docs forbid. The product surface has no independent bench_vitals check.  
**Fix:** Gate the Breathing/Heart dashboard tabs and the _dashboard_fields vitals string on config.sensors.radar.bench_vitals explicitly (defense in depth), or remove them from DASHBOARD_SENSORS entirely. Do not rely solely on the reader-level drop when the product surface advertises the tabs.

### 7. 🟠 HIGH — Only ONE notification per sustained cry episode — no re-alert during prolonged crying; notification_cooldown_seconds is dead code when soothe is off
*ship-safety · verdict: confirmed*  
**Where:** `src/beddington/state.py:42-43 (early return before re-notify) and :59-61, :80-86`  
**What:** In CryEventTracker._observe_above, once _active_start is set, every subsequent above-threshold window hits `if self._active_start is not None: return TrackerResult()` (line 42-43) BEFORE any re-notify check. _notification_due()/_last_notification_offset only run at the single moment of first activation (line 59-61). So a baby crying continuously for 20-30 min produces exactly ONE desktop notification at t=0. The documented knob `notification_cooldown_seconds` (README config table) only affects the START of a *later, separate* episode — test_state.py:46 only covers cry/stop/cry, never one long cry. If a tired parent misses or dismisses that single notification, there is no repeat alert for the ongoing cry. For a baby monitor, 'notify once and go quiet while the baby is still screaming' is a serious miss.  
**Fix:** Re-evaluate _notification_due on every window while _active_start is set, firing a repeat notify when now - _last_notification_offset >= notification_cooldown_seconds. Add a test asserting multiple notification_sent events during a single multi-minute cry.

### 8. 🟠 HIGH — Single delivery channel with no fallback: LocalNotifier is desktop-only; on a headless Pi the alert is just a print() to a log file
*ship-safety · verdict: confirmed*  
**Where:** `src/beddington/notifications.py:18-48; cli.py:388 (LocalNotifier is the only notifier)`  
**What:** LocalNotifier.notify() prints to stdout and tries an OS desktop notification (osascript on macOS, notify-send on Linux). On a headless Pi running under systemd, `notify-send` requires a DBus/graphical session that a --user service without an active login typically lacks, so _desktop() returns False and the ONLY surviving 'delivery' is `print()` into ~/beddington-*.log — which no parent is watching at 3am. There is no phone push, SMS, sound-alarm, or any network delivery. notify() returns {console:True, desktop:False} and the pipeline treats the alert as 'sent' (Event kind=notification_sent) even though nothing reached a human. This is a silent single-point-of-failure for the whole safety mission, and it fails SILENT: the events.json will claim an alert was sent.  
**Fix:** Add a delivery channel that actually reaches a parent off-device on the same LAN (loud local speaker alarm at minimum; a LAN push/webhook/ntfy for the parent phone as roadmap already implies). Have notify() report per-channel success and have the pipeline flag/log when ALL channels failed rather than recording notification_sent.

### 9. 🟠 HIGH — When auto-soothe is enabled in the always-on assistant, sustained crying is soothed but never alerted to a parent
*ship-safety · verdict: confirmed*  
**Where:** `src/beddington/cli.py:909-916 (_AutoSootheWatcher.feed -> _soothe_via_dashboard) and cli.py:2310+`  
**What:** listen-assistant is the deployed always-on service. Its _AutoSootheWatcher runs the same YAMNet cry signal and, when the shared auto-soothe toggle is on, plays a soothe sound via the dashboard (cli.py:911). But listen-assistant has NO notifier and never calls run_pipeline — so the cry it just detected is used to trigger sound, yet never produces a parent notification. Combined with finding #1 (no monitor service), the realistic deployed state is: assistant hears the cry, plays music, and no one is told. The safety invariant 'auto-soothe must never touch the alarm path' is technically honored (it doesn't suppress an alarm) — but the practical failure is the inverse: the alarm path isn't present at all in the process that IS detecting the cry, so soothing silently substitutes for alerting.  
**Fix:** Either run the alarm pipeline in the same always-on process as auto-soothe (so every detected sustained cry both soothes AND notifies), or make auto-soothe emit a notification alongside the soothe. Auto-soothe playing a sound must never be the only response to a detected cry.

### 11. 🟡 MEDIUM — Auto-soothe watcher runs on every frame including mid-voice-capture, so a cry trigger can start music into the buffer the assistant is transcribing

### 13. 🟡 MEDIUM — Two divergent _normalise_soothe_context implementations split the context-keyed soothe learning buckets
*newbugs-integration · verdict: plausible*

### 14. 🟡 MEDIUM — Assistant polls the liveview dashboard over localhost HTTP every ~2s for the entire night
*perf-pi · verdict: confirmed*  
**Where:** `src/beddington/cli.py:903-907 (_dashboard_soothe_playing) and cli.py:1789-1801 (_live_view_json / urllib.request.urlopen)`  
**What:** In the always-on wake-word loop, every iteration checks `if now - last_soothe_poll >= 2.0` and calls _dashboard_soothe_playing(port=8088), a blocking urllib.request.urlopen to 127.0.0.1 with timeout=3. That is ~1800 HTTP round-trips/hour, forever, purely to reconcile whether music is playing. It is on the same thread that must promptly consume mic frames from frames_q (maxsize ~100 at 30ms) — if the liveview service is briefly busy/GC-pausing, the urlopen can stall up to 3s, during which the mic queue drops frames (drop-oldest) and a wake word can be missed. It also hard-couples the assistant to the liveview HTTP service being up; if liveview restarts (and note the known crash-loop bug on config/demo.toml), every poll throws and is swallowed but still costs a connect attempt.  
**Fix:** Replace the per-2s HTTP poll with the existing shared-state file mechanism (autosoothe.json is already read this way) or a lightweight IPC, and move any remaining HTTP reconciliation off the mic-consuming thread so a slow/absent liveview never stalls frame draining.

### 15. 🟡 MEDIUM — YAMNet model file (~4MB) is fully SHA256-hashed on every detector construction
*perf-pi · verdict: confirmed*  
**Where:** `src/beddington/detector.py:118-119 and 147-153 (ensure_model -> _verify_hash reads entire file)`  
**What:** YamNetTFLiteDetector.__init__ calls ensure_model(), which when the cached model exists calls _verify_hash(destination) = hashlib.sha256(path.read_bytes()). This reads the whole model into memory and hashes it every single time a detector is built. Detectors are constructed in multiple places: the monitor run (cli.py:385), sounds-live (cli.py:1182), and crucially the auto-soothe builder (_AutoSootheWatcher._build_watcher -> YamNetTFLiteDetector() at cli.py:2483). Each toggle of auto-soothe rebuilds and re-hashes. It is wasted disk read + CPU on integrity-checking an already-verified local file; on a Pi this is a needless SD read + hash on every construction.  
**Fix:** Only verify the hash on first download/move, not on every load of an already-present cached file (or gate re-verification behind an env flag / mtime check). The download path already verifies before the atomic move at detector.py:142.

### 16. 🟡 MEDIUM — SQLite history runs at default synchronous=FULL, fsyncing every 10s append to the SD card indefinitely
*perf-pi · verdict: confirmed*  
**Where:** `src/beddington/sensor_store.py:48 (only journal_mode=WAL set; no synchronous pragma) and append() commit at :96-98`  
**What:** SensorStore sets PRAGMA journal_mode=WAL but leaves synchronous at the default FULL. Under WAL+FULL, each commit fsyncs the WAL. append() commits on every snapshot (every ~10s per config sample_interval, or per sampler tick), and the liveview service does the same, running 24/7 for weeks. That is a durable fsync to the SD card every few seconds forever for non-critical derived telemetry — a real SD-card write-endurance and I/O-wakeup concern on a Pi. WAL also means checkpoints periodically rewrite pages. This is low-stakes data (room temp/presence trends) that does not need FULL durability.  
**Fix:** Set PRAGMA synchronous=NORMAL (safe under WAL, fsyncs only at checkpoint) for the history store, and/or batch appends. Consider wal_autocheckpoint tuning. This meaningfully cuts SD writes with no meaningful data-loss risk for telemetry.

### 17. 🟡 MEDIUM — Sensor failures (BME688 {}, radar/PIR drop) fail silent — a dead sensor is indistinguishable from a calm nursery
*ship-safety · verdict: plausible*  
**Where:** `src/beddington/pipeline.py:227-238 (_read_sensor_sample swallows all exceptions to {}) and pipeline.py:116-118 (empty readings simply skip the event)`  
**What:** _read_sensor_sample catches every reader exception and returns {} (line 234-235); pipeline then only appends an environment_sample event `if readings` (line 118). So when the BME688 returns {} on ~half its reads (known hardware reality) or the radar/PIR drops off, the run simply records nothing — there is no 'sensor unhealthy' event, no degraded-mode flag, no surfacing to the parent. A parent asking 'is the room OK?' via the assistant gets silence or stale data with no indication the sensor is dead. For a monitoring product, a failed sensor must be visible, not invisible.  
**Fix:** Emit a sensor_unhealthy/degraded event (with which reader failed) when a reader raises or returns {} repeatedly, and surface 'I can't read the air sensor right now' in the assistant/dashboard rather than silently omitting it.

### 18. 🟡 MEDIUM — listen/analyze crashes on any per-window exception — one bad YAMNet inference kills the whole monitoring run with no restart
*ship-safety · verdict: confirmed*  
**Where:** `src/beddington/pipeline.py:77-159 (the for-window loop has no try/except); cli.py:403`  
**What:** run_pipeline's main window loop (pipeline.py:77) has no exception guard around detector.score / tracker.observe / notifier.notify. Any transient error (a malformed audio window, a numpy shape issue like the known WAV stereo-reshape crash, an interpreter hiccup, or notifier raising) propagates out of run_pipeline and terminates the `listen` process. Because there is no supervising service/loop (finding #1), the monitor does not come back — it just dies. Contrast with _read_sensor_sample and _classify_window_sound, which DO guard exceptions; the safety-critical score/observe/notify triple does not.  
**Fix:** Wrap per-window processing so a single-window failure is logged and skipped rather than aborting the night. Whatever long-running service wraps this must have Restart=always plus a heartbeat/watchdog so a full crash self-heals.

### 19. 🟡 MEDIUM — YAMNet model missing/corrupt on the Pi aborts detector construction before the loop — monitor never starts, no fallback
*ship-safety · verdict: confirmed*  
**Where:** `src/beddington/detector.py:116-153 (ensure_model raises on checksum mismatch / download failure), cli.py:385 (YamNetTFLiteDetector constructed eagerly)`  
**What:** YamNetTFLiteDetector.__init__ calls ensure_model, which raises RuntimeError on checksum mismatch (detector.py:149-153) and will attempt a network download (detector.py:123-128) if the cached model is absent. On a privacy-first offline Pi with no/limited network, or an SD-card-corrupted model file, detector construction throws at cli.py:385 and the monitor exits before entering the loop. There is no degraded 'model unavailable, alerting on raw loudness' safety fallback and (per finding #1) no service to retry. A silently corrupted model file = a silently dead monitor.  
**Fix:** Pre-stage and verify the model at install time; on model-load failure, fail LOUD (persistent visible/audible error) rather than a one-line exit, and consider a crude loudness-based backstop alarm so the device degrades to 'noisy = alert' instead of going dark.

### On-Pi performance — grade C
On-Pi viability is borderline-workable but has real sustainability risks. The audio callbacks are correctly kept light (copy+enqueue, drop-oldest queues), and SQLite history is bounded/pruned with WAL — those are good. The serious concerns are: (1) the background sensor sampler blocks ~2.25s of sleeps on EVERY tick, so its thread never idles and effective cadence drifts far off the configured interval; (2) memory budget on a 4GB Pi is tight-to-over when the assistant (Ollama llama3.2:3b ~2-2.5GB + Whisper + Piper + YAMNet) and the liveview service (rpicam-vid MJPEG) run concurrently as the two systemd units intend; (3) the assistant loop makes a blocking localhost HTTP round-trip to the liveview dashboard every ~2s all night for soothe reconciliation, coupling the two services and adding steady request churn; (4) YAMNet's full-file SHA256 is recomputed on every detector construction; (5) SQLite runs at default synchronous=FULL under WAL, fsyncing on every 10s append for SD-card writes forever. None are instant crashes, but they erode multi-hour overnight headroom.

- 🟠 HIGH **Background sensor sampler blocks ~2.25s of time.sleep on every tick, saturating its thread and skewing cadence** — `src/beddington/cli.py:1510 (_SensorSampler._run) -> _read_sensor_snapshot at cli.py:688-709`  
  Pass warm_seconds=0.0 in the sampler path (the readers are already warmed once at startup), matching the assistant loop which correctly uses warm_seconds=0.0 at cli.py:1061. Then the snapshot is just the 5x0.05s multi-pass (~0.25s) and self._stop.wait(interval) actually governs cadence.
